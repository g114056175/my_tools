## 已重現與修正

- 補查舊快照可能清掉等待期間收到的新影片回報。受控 Chromium 排程下，0.6.7 回傳空目標；修正版保留新影片。分頁／子 frame 換頁及快速補查也有失效保護。
- 同一文件重建控制程序會重用影片 ID，背景可能漏送選取通知。新版使用獨立身份；舊回報不會混入新控制程序。
- popup 重複 watch／回報會清除重建標示。新版同目標續用標示與速度提示節點，更新標題與位置。
- 更新入口、舊 API 檢查與延後回覆補上失效保護；受控失效後可建立新 API。一般程式錯誤仍會拋出。

## 本機固定資料

YouTube 結構 fixture 與本機影片完成 10 次 MPA 重載、10 次 SPA 換片；每輪確認已播放到 8×，且主影片目標可取得。12 次 popup 回報／watch 更新後，標示框與速度提示各維持同一個節點。

同文件保留舊背景目標後，處置並重新注入內容腳本，新 ID 與選取通知皆更新，後續新影片可套用 8×。子 frame 延遲由測試控制排程提供，不代表真實網站重現。

10 秒載入緩衝、背景停止探索與原有播放保留控制仍通過；三個 frame 的完整倍速儲存事件同步沒有額外設定請求。

## 真實 YouTube

公開頁以 popup 手動記錄 8×，再透過擴充功能設定 API 啟用跟隨。3 次重新載入與 3 次官方連結的站內 SPA 換片，都取得影片目標；等待正片開始後，實際速度為 8×，每段觀察到影片進度增加約 15–16 秒。

另有 5 次重新載入與 1 次 SPA 僅驗證辨識，沒有當作預設速度驗收。測試未登入，未遇到 CAPTCHA、地區或登入阻擋；網站廣告／導航請求仍有錯誤，未妨礙上述播放。

## 仍需確認

- Chromium 151、Brave 156 的更新、延後回覆與背景初始化測試，先驗證錯誤收集器確實能收集探針，再清空紀錄測試；未重現使用者回報的持續新增錯誤，不能宣稱此問題已解決。
- 背景儲存／DOM／分頁活動壓力測試已執行；CDP 凍結命令未通過頁面計時器停滯驗證，未列為有效凍結測試。
- Windows 介面讀取工具因無法確認 Brave 當前網址而停止，未取得使用者那筆錯誤的完整堆疊。使用者貼出的程式碼與 0.6.7 成品吻合。
- 原生工具列 popup 尺寸與所有網站／廣告組合未全面驗證；本輪介面回歸使用實際渲染的 420px 擴充頁面。未將 DOM 工作量換算為 CPU 使用率。
