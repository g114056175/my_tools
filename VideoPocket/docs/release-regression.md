# VideoPocket 發布回歸與量測摘要

目前發布 build：`size-binding-29`，擴充功能版本維持 `1.0.0`。

## 本次發布前驗證

- Node 測試：1,019 項，1,017 通過、2 略過、0 失敗。
- 本機 fixture-browser：9/9 通過，涵蓋社群播放器、共用欄位、X 引用卡片、標題優先序與欄寬、來源配對、畫質偏好及選片後探索。
- fixture-browser 使用本機 HTTP／合成或攔截的 DOM、JSON、Worker 與媒體資料，不能視為實站下載驗證。這 9 個本機開發執行器未隨原始碼發布；公開可重跑的測試以 `tests/` 為準。
- 新增 HLS 單一／多音軌大小規則與 YouTube 分軌平均值案例，確認不重複計算音軌、不把未綁定平均值當作檔案大小。
- 安裝資料夾、ZIP 與提交中的 extension 逐檔核對；保留原始發布日期、版本、圖示及既有 Demo 圖片／GIF。

在專案目錄執行：

```sh
npm ci
npm test
npm run build:observer
```

修改來源觀察器後須重建隨附 bundle；重建結果應與提交的 `extension/media-observer.js` 一致。

## 固定回歸清單

- [ ] 選片／標題：YouTube、Bilibili、X 引用影片／留言 GIF、Facebook、Reddit、Twitch 內嵌播放器。
- [ ] 動態頁面：換片、多播放器、主播放器／迷你視窗、開關 popup、重新整理與失效來源。
- [ ] 來源入口：JSON.parse、Response、XHR、適用的 Worker 與 blob／MSE；確認來源仍屬於所選播放器。
- [ ] 畫質：短邊解析度、最佳後綴、單一選項、偏好降級後不覆寫原偏好。
- [ ] 下載：直連 MP4、HLS／DASH、分離影音、未知長度、持續傳輸超過 20 秒、取消及錯誤清理。
- [ ] 片段：索引式局部傳輸、完整下載後裁切提醒、起迄時間與音畫同步、Smart Cut 回退。
- [ ] 字幕：頁面重新整理／導覽失效、重開 popup 保留本頁結果、延遲回應不可寫回舊影片。

以上勾選項是每次發布需評估的項目，不表示所有實站情境已通過。本版自動測試覆蓋固定資料，實站範圍如下。

## 既有實站證據與仍待測項目

下表保留先前 `performance-regression-27` 的證據，未冒充本次 build 的實站重新驗收。

| 樣本／情境 | 已有證據與限制 |
|---|---|
| Instagram 指定 Reel | 全片、5 秒片段、音訊實際下載與完整解碼通過；非整站保證 |
| TikTok 指定短片 | 全片、5 秒片段、音訊實際下載與完整解碼通過 |
| YouTube、Bilibili 一般頁、HLS basic | 該輪來源與畫質 inspect-only 通過，未重下載全片 |
| X OpenAIDevs 指定貼文 | 該輪獨立 Chromium 導覽 HTTP 403，未取得播放器，不算下載通過 |
| Facebook KFC、Bilibili 迷你窗 | 缺指定頁／情境的新實站證據，需人工重測 |
| Reddit、Threads、私人未知 blob 網頁 | 沒有本輪實站下載驗收；登入、human-check 或缺樣本可能阻礙驗證 |

來源配對測試通過、HTTP 200、inspect 成功與完整下載可解碼，是不同層次的證據；不得合併宣稱所有平台可用。

## 大檔與處理效能（既有 build 27 量測）

素材為有效 faststart H.264／AAC MP4，2,317,979,454 bytes，6242.28 秒，1280×720；以已編碼樣本 stream-copy 重複產生，非真實網站長片。Windows、i5-12600K、約 32 GB RAM，獨立 Chromium。HTTP 來源刻意忽略 Range，並節流至約 17 MB/s。

| 工作 | 下載 | 處理／驗證 | 儲存 | 結果 |
|---|---:|---:|---:|---|
| 全片 | 133.772 秒 | — | 7.374 秒 | 輸出 SHA-256 與輸入一致 |
| 完整下載後裁切 15 秒 | 134.867 秒 | 2.428 秒 | 0.072 秒 | 15.000 秒，完整解碼通過 |
| 下載中取消 | 約 5 秒時取消 | — | — | 約 5.784 秒結束，暫存清除 |

片段流程採樣峰值：約 693 MiB Private Bytes、926 MiB Working Set 合計、2.33 GB 影音暫存。這是約每秒一次的獨立 Chrome 進程採樣，不是嚴格上限，也未包含 OS 檔案快取與獨立 GPU VRAM。指定輸出位置為測試 profile 的 OPFS，不是人工另存對話框。三條流程結束後影音暫存均為 0 檔／0 bytes；使用者成品不算暫存。

起點為已驗證關鍵影格的合適單一 MP4，可省去時間軸正規化中間檔：本機 15／45 秒案例的暫存寫入量約減半，單次處理約 0.251／0.439 → 0.223／0.281 秒。非關鍵影格仍走既有 Smart Cut／精準轉碼。這些是特定電腦與素材的量測，不保證其他來源同速；本次發布未重跑數 GB 測試。

## 大小估算實測（獨立媒體量測）

下載兩部公開短片（60 秒及約 98 秒），測量 7 組畫質／音軌。先保存來源宣告平均位元率與時長，再下載所有影音分段，以 `-c copy` 封裝 MP4，並完整解碼核對。估值未使用下載後的位元率倒推。這是公式與實際媒體大小比較，非擴充功能整套下載驗收。

| 樣本 | 全片估算相對成品偏差 |
|---|---:|
| Apple Trailer 342p／432p／720p，對應音軌 | −0.13%／−0.06%／−0.02% |
| Angel One 144p／360p／576p，雙聲道 | ＋109.53%／＋28.17%／＋16.03% |
| Angel One 144p，六聲道 | −0.15% |

Angel One 的 HLS 平均值包含最大可播放音軌組合；雙聲道不能沿用六聲道的估值。同批素材再切為 38 個約 12–17 秒的來源分段區間，套全片平均值估算時落在實際大小的約 0.55–2.71 倍；Apple 全片雖準確，短區間仍約 −20% 至 ＋30%。

因此本版只有已知大小、單一完整格式平均值，或能唯一核對所選影音組合的 HLS 全片平均值，才顯示「約 …」。音軌組合不明或資料不足顯示「大小未知」，片段不套用全片平均值。

樣本與語意參考：[Apple 範例](https://developer.apple.com/streaming/examples/)、[Shaka Angel One 清單](https://storage.googleapis.com/shaka-demo-assets/angel-one-hls/hls.m3u8)、[RFC 8216 AVERAGE-BANDWIDTH](https://www.rfc-editor.org/rfc/rfc8216.html#section-4.3.4.2)。上述少量樣本不構成全部網站的統計誤差保證。
